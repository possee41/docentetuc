## Qué significa cerrado entre ejecuciones

| Modo futuro | ENABLED | LEASE_REQUIRED | ALLOWED_SOURCE | FDCI_EXTERNAL_ENABLED |
|---|---|---|---|---|
| Apagado total, estado actual a preservar | false | false | fdci | false |
| Servicio automático armado, solo mediante concesiones | false | true | fdci | true |

El segundo modo **no es cierre total**: la identidad autenticada y la apertura
autenticada permanecen disponibles. Sin concesión vigente, importación y
checkpoint se rechazan. Tras el cierre o el vencimiento, no hay permiso de
escritura; no existe un bypass permanentemente habilitado.

Esto reutiliza el mecanismo probado y evita entregar a Actions credenciales
de control Cloudflare para cambiar flags en cada corrida. Requiere que la futura
autorización acepte explícitamente mantener **el control de concesiones armado**.
Si se exige 503 también para toda apertura e identidad entre corridas, esta
alternativa no satisface esa condición: habría que diseñar otro control temporal
del plano de configuración. No se simulará ese cierre total con flags engañosos
ni se añadirá ahora infraestructura para conseguirlo.

El TTL es un cierre de escrituras **independiente de GitHub**: se comprueba al
recibir y de nuevo en los fences SQL de publicaciones/cursor. No requiere Cron
para expirar. No cancela HTTP en vuelo ni borra físicamente una fila vencida.
Tampoco revoca el secreto ni impide por sí solo una futura apertura autenticada.

**Ajuste pendiente:** el runner y workflow limitan TTL a 600 s, pero el gateway
genérico acepta hasta 900 s. Para el servicio automático, imponer en servidor
el máximo **600 exclusivamente a FDCI**, sin alterar los límites de otras fuentes.
No se afirmará que ese límite ya está implementado en servidor.

## Resultados que debe mostrar el resumen

Conservar `status` y ACK existentes; añadir interpretación en el resumen, sin
modificar elegibilidad o contar escrituras de control como publicaciones.

| Resultado visible | Criterio |
|---|---|
| Éxito con novedades | ACK válido sin fallo, `closed=true`, `created+updated>0`; indicar si el ciclo sigue parcial. |
| Éxito sin modificaciones | ACK válido sin fallo, cierre correcto, hubo examen pero no altas/actualizaciones; separar `unchanged` de `skipped`. |
| Sin comisiones activas; sin avance | `empty=true`, `examined=0`, `batches=0`, sin fallo ni fin de ciclo; indicar revisión/ciclo conservados. |
| Avance parcial esperado | `PARTIAL`, `failed=false`, `progressPending=true` por lote/presupuesto; continuar en el próximo horario, sin afirmar catálogo completo. |
| Error / resultado incierto | ACK ausente/inválido, `ERROR`, `failed=true`, `uncertain>0`, cierre no confirmado, o error de fuente/D1/autenticación/cursor. Suspender. |

Un vacío coherente no es fallo ni debe actualizar publicaciones, cursor,

## Freno de futuras corridas sin privilegios de escritura

Adaptación local pendiente del workflow: antes de entregar el secreto al runner,
consultar con `actions: read` la última corrida anterior del **workflow automático**.
Exigir terminación inequívoca satisfactoria de su job importador; ausencia de
evidencia, cancelación, timeout, fallo o cleanup fallido detienen el nuevo job.
No tomar el éxito de un job de resumen como éxito de importación.

Para arrancar por primera vez, exigir un marcador de bootstrap aprobado por el
dueño y ligado al SHA y a una corrida manual satisfactoria. Para reanudar tras
un incidente, exigir un reconocimiento explícito del ID fallido, por ejemplo
`FDCI_AUTOMATION_ACKNOWLEDGED_RUN_ID`. Solo permite superar ese ID exacto, no
cualquier error futuro; una siguiente corrida fallida tiene otro ID y se bloquea.
Es diseño pendiente, no una protección ya presente. La habilitación booleana
global por sí sola no implementa este freno.

Esta alternativa evita un PAT con permisos para que el job se desactive a sí
mismo. El historial de fallos conserva el bloqueo entre oportunidades, aunque
GitHub siga disparando jobs de preflight que no reciben el secreto ni importan.
Un fallo de API durante esa verificación también debe fallar cerrado. La
concurrencia compartida evita que se ejecuten dos importadores mientras se revisa.

## CPU, observación y condiciones de suspensión

Cloudflare Free tiene el límite HTTP de 10 ms ya registrado. La muestra del
último ensayo dio p99 máximo por grupo 3,112 ms; **no demuestra máximo individual**
ni el costo de dos escrituras, porque el catálogo estaba vacío. Conservar como
riesgo explícito la muestra previa y el hecho de que no hay entradas actuales.

Usar los Invocation Logs existentes del panel para consultar/exportar por versión,
hora, ruta y outcome CPU individual y duración separadas. No exportar Authorization,
cookies o secretos. El 403 de la API no se resuelve suponiendo permisos nuevos ni
equiparando wall time con CPU. Si no hay logs guardados no pueden recrearse.
[CPU por invocación](https://developers.cloudflare.com/changelog/post/2025-04-09-workers-timing/).

Suspender nuevos lotes y futuras importaciones ante:

- HTTP 1102 / `exceededCpu`, fallo D1, identidad o propietario incorrectos;
- CPU **individual observada >7 ms**, ACK incierto o limpieza fallida;
- 429 u otro error de fuente que el runner no considere un parcial esperado;
- ausencia de evidencia suficiente para reconocer la última ejecución satisfactoria.

El runner puede detenerse ante los errores HTTP y su cierre falla de forma visible.
**Hoy no consulta CPU individual ni implementa corte preventivo a 7 ms**. La
medición suele llegar después de ejecutar: no se pueden deshacer lotes confirmados.
El freno de historial no detecta por sí mismo una CPU >7 ms si el job terminó
success. Con el 403 actual, ese umbral exige revisión del operador en el panel y
apagado antes del siguiente horario. No es monitoreo desatendido demostrado.

Antes de activar, resolver ese acceso con permisos de lectura ya disponibles o
aceptar expresamente una observación inicial del dueño y el riesgo residual.
No contratar Paid ni añadir Tail Workers para evitar esta decisión. No convertir
datos ausentes en ceros. No repetir ahora una corrida vacía para inferir CPU con carga.

## Apagado y recuperación

**Control independiente de GitHub:** desde Cloudflare, restaurar la configuración
congelada cerrada del gateway tras revalidar identidad/hash/bindings/secretos.
`IMPORT_GATE_ENABLED=false`, `IMPORT_GATE_LEASE_REQUIRED=false`,
`IMPORT_GATE_ALLOWED_SOURCE=fdci`, `FDCI_EXTERNAL_ENABLED=false`.
No depender de obtener credenciales GitHub para ejecutar ese cierre primero.

Luego poner `FDCI_AUTOMATION_ENABLED=false`, deshabilitar solo el workflow
automático y cancelar su corrida si sigue activa. No cambiar el manual ni
reactivar el antiguo. Un flag detiene jobs futuros que lo consulten, no una
petición ya en vuelo; el cierre Cloudflare es el corte efectivo de acceso.
Ante sospecha de exposición, revocar solo la credencial automática con autorización.

Si el gateway aún está armado y hay una concesión propia, intentar cierre del
propietario; si no puede confirmarse, cierre total, espera de TTL/drenaje y consulta
acotada de concesiones. Sin borrar filas ajenas, restaurar D1 ni repetir publicaciones
de ACK incierto. Verificar 503, cero concesiones **vigentes**, ausencia de corridas
activas, cursor confirmado e integridad acotada de publicaciones. Conservar el
último checkpoint; reanudar únicamente tras decisión del dueño.
