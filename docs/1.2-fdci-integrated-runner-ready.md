# FDCI: runner oficial durable integrado, preparado localmente

Base: código local `a5eb78f`, publicación piloto `1e600b86e0f0aef0b6c0ad7692c7bd7fe9e16a11` y validación ya aprobada `42293226448`. **No se repitió esa ejecución ni se hicieron operaciones remotas de escritura, consultas FDCI, deploy o cambios de permisos.** Gateway HALTED y Cron intactos; cambios locales ajenos preservados.

## Comportamiento implementado

- `scripts/fdci-static-runner.mjs` une el recolector existente, `fdci-static-state` y la promoción. Conserva máximo dos cursos, seis solicitudes oficiales y pausas de 400 ms. Recupera estado con generación, checksum, SHA de blob y revisión ejecutable; no inicializa automáticamente estado faltante.
- Primero reconcilia cualquier publicación pendiente desde el estado confirmado. Si necesita repararla, termina sin volver a recolectar. `recovery_only` también permite confirmar una operación ambigua sin nuevas consultas, incluso si el puntero ya se había actualizado.
- `scripts/fdci-static-publisher.mjs` escribe únicamente en `possee41/docentetuc-fdci-catalog-pilot`, rama main, bajo `fdci-catalog/`: versión inmutable `versions/<checksum-del-documento>.json` y única referencia activa `active.json`. No toca `catalog.json` existente, workflows ni configuración de Pages.
- Estado, versión y referencia se escriben **en ese orden y en commits separados**. No hay transacción entre ramas ni atomicidad con el CDN. La versión existe y se valida antes de cambiar la referencia. Un fallo deja recuperables el estado confirmado, el puntero anterior y/o una versión huérfana reutilizable; no se hace rollback de datos ni se repite una escritura ambigua a ciegas.
- SHA condicional protege el cursor y el puntero ante carreras. Se rechazan generaciones antiguas, referencias inconsistentes y sobrescritura de versiones inmutables. Reconciliar exactamente el mismo estado no escribe nada.
- Vacío completo → versión vacía válida. Parcial/error → conserva la última versión completa y actualiza solo su referencia de estado/antigüedad. Sin catálogo completo previo no se publica ningún catálogo. Las proyecciones privadas/D1 quedan fuera del runner.

## Lectura web sin permisos adicionales

`lib/fdci-static-publication.ts` valida referencia y versión, evita regresiones, devuelve copias independientes y conserva la última válida como stale si hay corrupción, incoherencia o falta de propagación. Nunca interpreta indisponibilidad como catálogo vacío válido. Sin copia previa en memoria puede devolver unavailable; no promete disponibilidad absoluta durante fallos CDN.

Los commits de Actions con `GITHUB_TOKEN` **no disparan builds de Pages**, según la [documentación oficial](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site). No se añadieron permisos Pages, PAT ni un despliegue paralelo. Se prepara lectura directa del JSON estático desde el CDN de GitHub:

```text
https://raw.githubusercontent.com/possee41/docentetuc-fdci-catalog-pilot/main/fdci-catalog/active.json
```

Allowlist exacta de ese repositorio/rama/ruta; versiones derivadas únicamente de checksums verificados. Acepta `text/plain` de raw solo en ese origen, valida JSON/esquema/hashes, omite credenciales y rechaza redirecciones. El URL equivalente de Pages sigue admitido para una publicación futura autorizada, pero no se presume que Pages se actualice con estos commits. **CORS y propagación real del nuevo origen todavía NO VERIFICADOS**; no se cambió la app ni el feed sintético actualmente visible.

## Preparación de ejecución y seguridad

`docs/examples/fdci-static-integrated.yml.example` permanece local y fuera de los workflows activos: solo manual, apagado salvo `FDCI_INTEGRATED_ENABLED=true`, recuperación sin consultas como valor predeterminado, mismo grupo de concurrencia que la persistencia y `contents:write` ya previsto. No incorpora permisos nuevos. Ese permiso sigue siendo amplio dentro del repositorio; los límites de ruta/rama son controles del código.

El checkout apunta al SHA ejecutable aprobado, comprobado también por el runner. Esto permite que main reciba commits de datos sin confundirlos con una nueva revisión de código. Cambiar el ejecutable requiere una revisión explícita del estado, nunca un reset: `review-local` verifica el blob/checksum/revisión anterior, conserva checkpoint, catálogo y fecha real de intento, actualiza la revisión aprobada e incrementa la generación. No reinterpreta la cancelación controlada de la validación anterior como una consulta oficial reciente.

`node scripts/package-fdci-static-runner.mjs` genera en `.wrangler/fdci-integrated-package/` solamente runner Node autónomo, workflow manual y manifiesto con hashes de entrada/salida. Reutiliza esbuild instalado; el runner de Actions no requiere instalar dependencias. Los CLI de importadores ajenos a esta ejecución y el envío al gateway quedan fuera del bundle. Nada se publica al ejecutar el empaquetado local.

## Verificación y siguiente operación mínima

**10/10 pruebas locales de extremo a extremo aprobadas**: estado→versión→referencia, idempotencia, duplicados, vacío legítimo, error/parcial, fallo de commit de estado, fallo de versión/puntero, ACK perdido, versiones huérfanas, reparación sin consultar otra vez, carreras, conflicto inmutable, regresión y huecos CDN, revisión de código y lector raw. GitHub y FDCI se simularon íntegramente. TypeScript y lint focalizado correctos; paquete generado y sintaxis Node comprobada. No se ejecutó carga ni se repitieron ensayos remotos.

Riesgos restantes: transporte/publicación del nuevo protocolo y CORS necesitan su validación aislada; GitHub/CDN no ofrecen aquí una garantía de latencia, capacidad o almacenamiento ilimitado. Dos cursos por lote no garantizan un recorrido completo dentro de 24 horas ante un catálogo activo grande. Versiones e historial consumen almacenamiento. Una modificación administrativa externa puede requerir revisión manual; el código falla cerrado ante discrepancias.

**Operación remota mínima, con autorización independiente:** publicar selectivamente el paquete en el piloto; revisar el nuevo SHA ejecutable contra el estado vigente sin perder progreso; ejecutar una sola validación `recovery_only=true` y comprobar referencia, versión, hashes y lectura/CORS desde el origen Canary, sin modificar su Worker. Usar el estado vacío ya confirmado solo si el preflight verifica que sigue siendo ese estado; detenerse ante cambios. No consultar FDCI ni activar Cron o publicación productiva como parte de ese ensayo. El `catalog.json` público actual debe permanecer idéntico.
