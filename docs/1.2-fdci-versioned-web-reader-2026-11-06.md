# Lector FDCI versionado — integración local

Base: `a6c89ce`, rama `feat/1.2-final-integration`. Sin operaciones remotas.

- El modo `fdciCatalogTest=1` en Canary (o localhost para pruebas) consulta exclusivamente `fdci-catalog/active.json` del repositorio autorizado y su `versions/<sha256>.json`. El dominio productivo no habilita esta integración.
- Referencia sin caché del navegador; versión inmutable con caché. Ambas solicitudes GET usan CORS, omiten credenciales, rechazan redirects y tienen límites de tamaño/tiempo. Se validan formato, generación, ruta, hashes y fechas antes de componer la pantalla.
- Un catálogo oficial vacío es válido: elimina la proyección externa, no las capacitaciones D1. D1 conserva prioridad por ID o identificador externo bajo ambas denominaciones de fuente. Los datos administrativos no se sobrescriben.
- DEMO antiguo rechazado; no existe fallback a `catalog.json`. `FDCI_CANCELLED` se presenta como verificación interrumpida, no como fallo actual de la fuente. La fecha mostrada es la última actualización exitosa del catálogo, nunca la fecha inferida de modificación de un curso.
- Una referencia anterior, un documento corrupto o un error conservan la última pareja verificada como desactualizada. La protección cubre también respuestas concurrentes fuera de orden. Esta recuperación es en memoria durante la sesión: una recarga sin red vuelve a D1. Tras recargar, no hay un mínimo de generación persistido; una referencia CDN antigua válida puede observarse hasta su propagación, con su fecha real visible.

## Acciones privadas

Registros solo externos: sin Guardados, Agenda, recordatorios ni IA. La metadata conserva generación y checksum para identificar su procedencia. Se retiró la materialización automática del servidor que aceptaba el DEMO antiguo; una acción sobre un ID FDCI inexistente en D1 devuelve 409 sin crear publicaciones. Los registros ya existentes en D1 conservan sus flujos habituales.

**El flujo privado externo no está validado ni habilitado.** Antes de habilitarlo, servidor y cliente deberán comprobar la misma referencia/generación/checksum mediante el validador compartido, validar la publicación contra esa versión y completar una prueba E2E autorizada. No se materializan datos sintéticos.
