# /api/public-app — caché pública local de 60 segundos

30/10/2026. Base: `7869fbaf51f73aebeeb8284b8dd26cb99d9c14da`, rama `feat/1.2-sync-integration`. Se leyeron AGENTS.md y el informe local de escalabilidad. No se consultó Cloudflare ni D1 remota y no se desplegó nada.

## Aptitud y alcance

El handler no recibe identidad ni consulta cuentas, sesiones, perfiles, Agenda, guardados o notificaciones privadas. Hace exactamente dos SELECT: `APP_PUBLICATIONS_QUERY` sobre publicaciones del catálogo público (máximo 400 resultados) y `source, synced_at, last_attempt_at, last_successful_sync_at, sync_status` de `sync_state`. No selecciona errores libres de diagnóstico. `profile`/`publicProfile` son null y los arrays privados están vacíos para todos los visitantes.

La conclusión de privacidad se apoya en el código y esquema actuales y pruebas sintéticas, no en una inspección de datos personales reales. `publications.metadata` sigue siendo el metadato público de fuentes ya expuesto por esta API; esta tarea no redefine su contrato. No se deben introducir datos privados en esa tabla ni personalizar este handler sin retirar/revisar su caché. Se conserva SELECT y cuerpo JSON sin cambios de formato.

Actualmente ningún parámetro de consulta afecta el resultado. Se cachea exclusivamente `GET /api/public-app` **sin parámetros**. Cualquier query string, otro método/ruta o flag de apagado evita tanto la lectura como la escritura de caché. Los parámetros siguen recibiendo el comportamiento original, sin supuestos sobre filtros futuros.

## Implementación

- Cache API nativa `caches.default`. Clave construida desde origen y ruta fija, con versión de configuración; nunca se copia la petición, sus cookies, Authorization ni identificadores de instalación.
- Solo se almacena la respuesta JSON 200 construida por el handler después de completar ambas consultas. Los 503 y los resultados incompletos no se almacenan. No se consulta identidad al servir HIT.
- Entrada interna `Cache-Control: public, max-age=60` y fecha límite absoluta calculada antes de las consultas D1. El lector rechaza entradas vencidas, de tipo/status inesperado, privadas o con Set-Cookie. Los HIT no renuevan el vencimiento y no existe stale-if-error ni revalidación en segundo plano.
- Toda respuesta hacia navegador/proxy lleva `Cache-Control: no-store`, para evitar encadenar otra ventana de caché. El header interno de vencimiento se retira. El frontend conserva su política de fetch; no se modificó su copia offline preexistente.
- Diagnóstico público seguro: `X-Public-App-Cache: MISS`, `HIT` o `BYPASS`. Un MISS indica una consulta a D1; no garantiza almacenamiento posterior si Cache API no pudo guardar. Si falla Cache API, se consulta D1 y se devuelve su resultado o error real, sin inventar datos.
- Sin endpoints de invalidación, bibliotecas, migraciones, cambios de autenticación ni cambios en otros módulos.

Las operaciones existentes de importación actualizan D1 y no invocan un invalidado de este endpoint. Sus cambios/estado de sincronización podrán tardar hasta 60 s en aparecer aquí. «Recargar» dentro del TTL puede recibir la misma selección pública, pero continúa consultando datos guardados y no dispara sincronizadores. Fechas y salud originales se conservan: la caché no convierte PARTIAL en OK ni cambia fechas de verificación. Los detalles/búsquedas y la validación privada de acciones siguen sin esta caché.

## Apagado, invalidación y rollback futuros

No se modificó ningún archivo Wrangler ni variable remota.

1. **Desactivar:** configurar `PUBLIC_APP_CACHE_ENABLED=0` (también admite `false`) en una versión futura autorizada. Evita match/put incluso con entradas existentes. Ausente o distinto de esos valores: mecanismo habilitado.
2. **Invalidar sin purgar:** cambiar `PUBLIC_APP_CACHE_VERSION` a un valor nuevo, por ejemplo `public-app-20261030-2`, en una publicación de configuración autorizada. La clave anterior deja de usarse en esa versión. Valor por defecto: `v1`. No es secreto ni se acepta desde query strings.
3. **Urgencia durante un despliegue gradual:** verificar que todas las versiones que atiendan tráfico usan el apagado/versión nueva; cambiar una versión no altera instantáneamente las otras. Alternativa: volver al código previo, que no consulta esta caché. D1 permanece igual.
4. Sin operación adicional las entradas vencen en hasta 60 s. No se añadió botón público para forzar MISS; no se prometió invalidación global mediante `cache.delete` local.

- Fallos D1 antes de crear una entrada y después de vencer devuelven 503; sin cachear error ni servir snapshot vencido. Un pedido posterior válido vuelve a MISS.

También pasó la prueba existente `lib/app-publications-query.test.ts` (**1/1**), TypeScript `--noEmit`, ESLint focalizado de los dos archivos de código y `npm.cmd run build`. No fue un fallo D1 ni remoto. Los errores SYNTHETIC_D1_FAILURE de la prueba son inyecciones esperadas.

Muestra comparable: mismo Workerd, DB, consulta, payload y cinco GET secuenciales por condición; sin caché mediante flag versus caché habilitada. Ambos recorridos se ejecutan después de los casos funcionales. D1 mide las consultas de lectura del handler; se excluyen la creación/modificación de fixtures.

La opción BYPASS conserva el acceso D1 original; la comparación no implica ahorro demostrado en la factura, CPU o invocaciones Worker.

## Limitaciones y siguiente paso

Cache API tiene entradas por centro de datos; no se replican como un caché global y pueden ser desalojadas antes de 60 s. Solicitudes concurrentes en MISS pueden consultar D1 varias veces; no se añadió bloqueo global ni coalescencia. La escritura de caché se espera en la petición y puede añadir latencia al MISS. Si no existe Cache API se sirve D1 normalmente. El primer despliegue futuro de este código habilitaría el mecanismo por defecto, salvo flag explícito de apagado.

El beneficio depende de reutilización por origen/centro de datos; no elimina el costo de la consulta inicial, el límite de CPU ni las invocaciones al Worker. No demuestra capacidad para 20.000 usuarios ni margen en Free. Comportamiento oficial: [Cache API de Workers](https://developers.cloudflare.com/workers/runtime-apis/cache/).

**Recomendación:** autorizar posteriormente una prueba del build en un entorno web aislado con D1 sintética, sin tocar el canary de recordatorios: MISS → HIT, dos usuarios ficticios, expiración real de 60 s, apagado y nueva versión de clave. Medir CPU/outcome reales, filas D1 y estado de respuestas; ninguna carga masiva ni despliegue productivo. Esta tarea no creó ni modificó ese entorno.
