# FDCI: prototipo local de catálogo estático

**APTO para continuar una prueba aislada de consulta pública; no sustituye todavía FDCI en la aplicación.** Base `4d6497e`. No se accedió a D1 ni al gateway, ni se consultaron fuentes reales. Sin tokens, secretos, Workers, Cron, deploy, push o merge. El estado remoto HALTED no se modificó. Cambios ajenos conservados.

## Implementado

- `scripts/fdci-static-catalog.mjs`: reutiliza `collectFdci` y su normalización, `scope=active`, máximo seis solicitudes oficiales incluyendo reintentos, pausas de 400 ms. Necesita un fetcher explícito; la CLI solo permite demo sintética. Fallo de fuente, detalle faltante o catálogo que no cabe en el presupuesto => no se publica una recolección parcial. Con seis solicitudes pueden completarse hasta cuatro cursos distintos por corrida; no se promete cubrir un catálogo mayor ni actualizarlo en 24 horas. No se modificó el recolector.
- `lib/fdci-static-catalog.ts`: contrato público separado de D1/estado privado; lista cerrada de campos, IDs estables de comisión, orden determinista, schemaVersion, fecha UTC, versión SHA-256 del contenido e integridad SHA-256 del documento. Mismos registros normalizados y fecha producen los mismos bytes; una nueva observación actualiza la fecha y checksum sin cambiar la versión de contenido si no hubo cambios. Estados derivados pueden cambiar con el tiempo según las reglas del recolector existente.
- No se serializan metadata cruda, payloads de origen, tokens, perfiles ni sesiones. Los campos públicos se presentan como texto, no HTML ejecutable. SHA-256 detecta corrupción; **no autentica un alojamiento comprometido**: la confianza sigue dependiendo de HTTPS y del repositorio autorizado.
- Publicación local: lock exclusivo, JSON validado en temporal, versiones conservadas por checksum y un rename en el mismo sistema de archivos para reemplazar `catalog.json`. Generación/promoción fallida conserva el catálogo anterior; se rechazan publicaciones atrasadas o contradictorias con igual fecha. Un crash puede dejar un lock: revisar el proceso antes de retirarlo; no se elimina automáticamente por antigüedad. No se promete durabilidad frente a corte eléctrico ni atomicidad global entre nodos CDN.
- Lector opt-in para DocenteTuc: URL HTTPS fijada a `possee41.github.io`, sin credenciales/redirecciones; respuesta limitada a 2 MB/10.000 registros, esquema/checksum verificados. Retiene el último catálogo válido en memoria; devuelve `ready`, `stale` o `unavailable`, fecha y DTOs públicos. Más de 24 horas o fallo con respaldo => `stale`. Un vacío válido es `ready` con cero elementos. Sin respaldo válido, un error nunca se presenta como catálogo vacío actualizado. Tras recargar la página, si no hay red, no existe persistencia offline del último catálogo: se informa `unavailable`.

## GitHub Pages y publicación futura (no configurados)

GitHub Pages admite repositorios públicos en GitHub Free, sitio hasta 1 GB y límite blando de 100 GB/mes; puede limitar tráfico. No garantiza capacidad ilimitada. Debe comprobarse además que el uso del catálogo educativo público cumpla las restricciones del servicio, que excluyen hosting orientado principalmente a transacciones comerciales/SaaS comercial. [Límites oficiales](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

Propuesta: un workflow inicialmente manual, SHA revisado, `concurrency` único sin cancelación en curso; build/generación/validación antes de upload y deploy. Desplegar solo el directorio del catálogo, **nunca el repositorio o `.wrangler` completo**. `needs: build` evita desplegar si falla la generación, dejando la publicación anterior sin tocar. Un documento autocontenido evita mezclar índices y datos de diferentes versiones por caché; el lector rechaza corrupción/retrocesos. Conservar la versión previa validada y el artifact anterior para rollback explícito, sin depender de que el workspace efímero de Actions persista.

El job de publicación necesitaría únicamente los permisos GitHub documentados `pages: write` e `id-token: write`, con su entorno protegido; no un token Cloudflare, D1 ni un secreto nuevo mantenido por el usuario. No se creó un workflow ejecutable ni se configuraron permisos. [Procedimiento oficial Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Diferencias frente al sistema actual

- Es una fotografía pública del catálogo activo: no importa publicaciones, no mantiene historial/cursor/auditoría de importación en D1 ni modifica `sync_state`. Las versiones estáticas permiten comparar y recuperar fotografías; no equivalen a esa auditoría.
- Búsqueda SQL, filtros/recuentos del backend y RAG siguen leyendo D1. No incorporarán el JSON automáticamente.
- Guardados, Agenda, seguimiento y recordatorios pueden depender de IDs existentes en D1. No habilitarlos para registros solo estáticos sin una adaptación específica. Los actuales permanecen intactos.
- Las ediciones administrativas de D1 no se reflejan en el JSON. Integrar ambas fuentes requeriría definir precedencia, deduplicación y exclusiones; no se implementó ni se mezclaron datos ahora.
- Las fechas/estados se congelan entre generaciones y no se afirma actualización en tiempo real. No se deduce eliminación histórica por ausencia de una fotografía activa.
- El consumo se traslada a Actions y al alojamiento estático; no se acreditó todavía ancho de banda, CORS o caché de un Pages real. No se promete un ahorro medido ni cuota suficiente para toda DocenteTuc.
