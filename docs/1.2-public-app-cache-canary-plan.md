## Artefacto diagnóstico preparado localmente

```powershell
node scripts/prepare-public-app-cache-canary.mjs
```

Genera únicamente archivos ignorados en `.wrangler/public-app-cache-canary/`: `worker.mjs` y `wrangler.jsonc`. No ejecuta Wrangler ni llamadas HTTP. Valida el nombre/UUID de la configuración canary existente y compila **el GET real** y su Cache API, sustituyendo solo `getD1()` por un contador de los dos SELECT exactos permitidos. `AsyncLocalStorage` nativo mantiene las métricas por petición sin variables globales compartidas entre solicitudes concurrentes. No se agregaron dependencias.

El build no incluye las otras rutas web, autenticación, IA, importadores, retención, recordatorios ni envío push. No acepta SQL desde Internet. El acceso instrumentado solo expone `.all()` para la consulta del catálogo y la de salud; valida `meta.rows_read` y cero escrituras. La identidad del binding remoto se comprobará por metadatos y una lectura de `import_gateway_identity` antes de habilitar, fuera de las tres peticiones medidas: no se añade una consulta de identidad a los HIT.

La configuración generada empieza con `PUBLIC_CACHE_TEST_ENABLED=false`, `PUBLIC_APP_CACHE_ENABLED=0`, sin runId ni vencimiento. Devuelve **503 antes de D1**. El único recurso a desplegar posteriormente sería el Worker web canary existente; el build reemplaza temporalmente su interfaz por el endpoint de diagnóstico. Se debe reservar esa ventana de uso: no se hace sobre una candidata que otra persona esté revisando.

Para abrirlo posteriormente se necesitan valores explícitos:

- `PUBLIC_CACHE_TEST_ENABLED=true` y `PUBLIC_APP_CACHE_ENABLED=1`.
- `PUBLIC_CACHE_TEST_DATABASE_ID=853e2f5d-89b1-46a3-9c1c-5cbd46784756`.
- `PUBLIC_CACHE_TEST_RUN_ID=cache-<identificador único>` y `PUBLIC_APP_CACHE_VERSION` con ese mismo valor nuevo para garantizar caché vacía.
- `PUBLIC_CACHE_TEST_UNTIL` UTC válido, **como máximo cinco minutos en el futuro**. Fuera de esa ventana vuelve a 503 aunque se abandone el cliente. Abrir no crea un schedule.
- Metadata nativa `VERSION_METADATA` presente y una única versión canary activa al 100 %.

Las solicitudes deben llevar `X-Public-Cache-Test-Run` con el runId aprobado y `X-Public-Cache-Test-Step: miss`, `hit` o `expired`. El runId es un marcador de correlación **no un secreto ni autenticación de usuarios**; solo se exponen datos sintéticos que ya son públicos. No se crean secretos ni se usan cuentas/sesiones reales. Rutas, métodos, parámetros o marcadores no permitidos dan 404 cuando está abierto.

Cada respuesta conserva el cuerpo público y agrega headers de diagnóstico: versión, consultas y filas leídas/escritas. El log `public_app_cache_canary` contiene runId, paso, versión, estado, HIT/MISS y métricas D1 por consulta. No registra cookies, Authorization, payload, títulos privados ni credenciales.

La configuración habilita Observability al 100 % solo para la futura ventana del canary. **CPU se obtiene de los registros nativos individuales de Cloudflare**, correlacionados con esos logs y la versión; no se calcula en JS. El empaquetado diagnóstico agrega instrumentación y logging, de modo que su CPU incluye ese costo y no es una medición del build web completo. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).

## Criterios de decisión y riesgos

**Aprobación de esta muestra:** tres respuestas con versión inequívoca y HTTP 200; secuencia MISS/HIT/MISS; D1 2/0/2 consultas y cero escrituras; contrato y contenido público equivalentes, sin privados/cookies/tokens; CPU individual **≤7 ms** en las tres, outcome `ok`, ningún 1102/exceededCpu y cierre 503 demostrado. Es un umbral preventivo de prueba, no prueba de p99 ni capacidad de 20.000 usuarios. La CPU del diagnóstico no autoriza por sí sola el despliegue del build web completo.

**Rechazar y cerrar:** identidad/binding incorrectos, filtración privada, escrituras, D1 inconsistente, contrato distinto, errores de recursos, CPU >7 ms o cualquier efecto en recursos fuera del canary. No restaurar bases automáticamente.

**Inconcluso y cerrado:** falta una CPU/versión correlacionable, Cache API no ofrece HIT en ese entorno, cambio de centro de datos, otro tráfico contamina el ensayo o se vence la ventana antes de terminar. No sustituir CPU por wall time ni interpretar un 200 como aprobación de rendimiento. La falta de evidencia no justifica una repetición automática.

**Desactivación posterior de la caché:** `PUBLIC_APP_CACHE_ENABLED=0` en el recurso/versión autorizado; cambiar `PUBLIC_APP_CACHE_VERSION` evita reutilizar una clave antigua. En el diagnóstico también cerrar `PUBLIC_CACHE_TEST_ENABLED`. Cambiar flags locales no cierra un Worker remoto ya desplegado: hay que confirmar el despliegue efectivo o esperar el vencimiento como protección adicional, y verificar HTTP 503. Nunca afirmar cierre solo porque terminó el proceso Node.

Riesgos residuales: expulsión/aislamiento por centro de datos, carrera de MISS concurrentes, hasta 60 s de desfase, overhead de instrumentación, disponibilidad/retención de logs y uso compartido de la D1 canary por ensayos antiguos. No hay demostración remota actual ni garantía de margen CPU con esta preparación.
