## Defectos encontrados y corrección mínima

1. Dos aperturas simultáneas de la misma fuente devolvían 200/200: la comprobación previa y el UPSERT no eran atómicos. Ahora el UPSERT solo sustituye una concesión cuya expiración SQL está comprobada; la otra ejecución recibe 409.
2. El cierre no identificaba a la corrida propietaria y borraba la fila sin condición de titular. Un job cuyo open fallara podía ejecutar su `always()` y cerrar el job ganador. Ahora `opened_by` contiene el ID de ejecución y DELETE exige fuente y propietario. No se cambió el esquema 0031. Una segunda lectura confirma cierre y no oculta una falla D1.
3. Aperturas repetidas del mismo titular son idempotentes: no renuevan el TTL ni escriben. Un cierre no puede borrar una concesión de otra fuente incluso si cambia después de la lectura inicial.
4. `IMPORT_GATE_RUN_ID` identifica la corrida; GitHub fija el mismo ID/intento en open y close. El runner exige ACK de fuente/titular correcto y fecha válida. Un operador manual debe conservar el mismo ID. **Gateway y runner deben actualizarse juntos**: el cliente nuevo no acepta un ACK antiguo sin propietario.
5. El límite por fuente también se aplica a operaciones de concesión, no solo a importaciones.

`IMPORT_GATE_ENABLED=false` **no contradice** `IMPORT_GATE_LEASE_REQUIRED=true`: el modo temporal permite verificar identidad y gestionar una concesión autenticada, pero cada importación exige concesión futura de su fuente y el flag propio de FDCI. Ambos flags false dejan el gateway cerrado, antes de D1. No se utilizó apertura permanente.

## Decisión y límite de esta validación

**Validación funcional canary satisfactoria con las correcciones**, sin activar la automatización. El alcance fue el conjunto activo de dos comisiones de una captura, no el catálogo completo ni una garantía de consumo futuro. La concesión limita nuevas admisiones: no cancela una petición ya admitida cuando vence. Los runners deben respetar open/import/close y la concurrencia del workflow; el secreto de fuente sigue autorizando operaciones dentro de su ventana.

Antes de una activación definitiva se necesita una autorización nueva para revisar/publicar el SHA corregido, aplicar 0031 y actualizar gateway/runner en el destino aprobado, mantener un único escritor y configurar la automatización protegida. No se hicieron esas operaciones. Las métricas cercanas al umbral preventivo de 7 ms aconsejan conservar lotes pequeños y monitoreo; los cuantiles no certifican un máximo por invocación.
