## Qué explica el 403 y qué no

La credencial funciona para metadata y corresponde a la cuenta correcta. La
API rechazó específicamente el acceso a telemetry/query por autorización; el
cuerpo no informa una regla/permission ID más precisa. No fue un timeout, error
D1, 1102, respuesta de fuente oficial o rechazo del gateway de importación.

La [referencia oficial del endpoint](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/)
documenta `Workers Observability Write` como permiso aceptado para ejecutar
consultas, aunque esta operación solo lea telemetría. La sesión Wrangler usa
OAuth estándar; sus scopes publicados por `whoami --json` no incluyen un scope
específico de Observability. Esto es coherente con la denegación; no se puede
atribuir a una política interna concreta que el servidor no identificó.

No se solicitaron permisos Write ni un nuevo token, ni se intentó eludir el
403 con cookies o credenciales del navegador. La documentación de
[roles de Workers](https://developers.cloudflare.com/workers/authorization/workers/)
también describe Metadata Read-Only para observabilidad. No se presupone que
esa descripción cambie el requisito efectivo del endpoint para esta sesión;
no se creó ni probó otra identidad o política.

La retención documentada de Workers Logs Free es **3 días** al 3/11/2026;
la prueba ocurrió aproximadamente una hora antes. Por ello **la antigüedad no
explica el 403**. Habilitación, muestreo o cuotas podrían afectar existencia o
completitud de los eventos, pero no se midió una pérdida por esas causas.
Un 403 no permite distinguir un dataset vacío de uno con registros guardados.

## Recuperación sin ampliar permisos

El dueño puede abrir el Dashboard con su sesión habitual:

1. Workers & Pages → `docentetuc-import-1-2` → Observability/Logs.
2. **No pulsar Enable, Save o Deploy**. Comprobar si Logs aparece deshabilitado.
3. Seleccionar el intervalo anterior respetando la zona horaria del panel y la
   versión temporal `35462b7c-4184-4f70-984b-b291c9b7d238`.
4. Abrir Invocation Logs, no la gráfica de percentiles. Si existen, recuperar
   solo request ID/Ray ID, Worker, versión, ruta, timestamp, HTTP, outcome,
   `cpuTimeMs`, `wallTimeMs` y marcas de muestreo/truncamiento.
5. Omitir cabeceras Authorization, cookies, cuerpos de solicitud, tokens y
   datos personales. Un panel vacío, deshabilitado o sin campos individuales
   mantiene la medición como pendiente; no habilitar nada bajo esta autorización.

[Cloudflare documenta CPU y wall time por invocación](https://developers.cloudflare.com/changelog/post/2025-04-09-workers-timing/).
El Dashboard es una posibilidad de recuperación, **no una lectura ya realizada**
por el agente. Si no se recolectaron o fueron descartados, no hay recuperación
retroactiva garantizada. No hay otro endpoint de solo lectura demostrado aquí
que resuelva el 403 con la misma autenticación.

`wrangler tail` no recupera historial. La versión instalada implementa su
apertura con POST de sesión y limpieza DELETE; no se ejecutó bajo esta etapa
de lecturas estrictas. Además, el formato documentado de live logs no garantiza
`cpuTimeMs` y puede muestrear/descartar eventos: no sustituye Invocation Logs.
[Límites de real-time logs](https://developers.cloudflare.com/workers/observability/logs/real-time-logs/).

## Interpretación de métricas

| Dato | Qué demuestra |
|---|---|
| `cpuTimeMs` de Invocation Log identificado | CPU remota de esa invocación concreta |
| p50/p90/p99 de Analytics | Distribución agregada del grupo, no máximos individuales ni cobertura completa |
| `wallTimeMs` | Duración transcurrida de esa invocación, incluye esperas |
| `elapsedMs=3059` del runner anterior | Duración de la ejecución Node, no CPU Cloudflare |
| `exceededCpu` o HTTP 1102 | Incidente de recursos; suspender aunque falte el número CPU |

La muestra anterior sigue siendo 11 invocaciones agregadas, cero errores y
p99 máximo **por grupo** de 3,112 ms. No se volvió a consultar Analytics ni se
lo convirtió en un máximo individual, siquiera en un grupo con una solicitud.
Node/Workerd locales no producen CPU facturable remota.

## Contrato del lector local, cuando haya una exportación válida

No se implementa un lector API ficticio ni se conecta un bypass al runner.
El diseño mínimo es un validador local de exportación/manifest, sin dependencias:

- Manifest de la corrida: run ID, propietario, Worker, versión, intervalo y
  lista de peticiones esperadas con ruta, método, hora y correlación de respuesta.
  No basta cantidad de llamadas. En una futura prueba se deberán capturar IDs
  de correlación sin credenciales; la corrida anterior no dejó ese manifest
  completo, por lo que no puede declararse completa solo por encontrar 11 logs.
- Cruzar cada petición con un Invocation Log por request ID o por Ray ID explícito
  del evento. No suponer que ambos IDs son intercambiables ni adivinar por el
  horario. Comprobar Worker, versión, ruta y ventana temporal exactos.
- Exigir CPU numérica finita >=0, outcome válido y ausencia de truncamiento,
  muestreo incompleto, IDs duplicados/conflictivos o peticiones sin evento.
  Los eventos ajenos no rellenan huecos. Paginar una exportación limitada o
  declararla incompleta: nunca asumir que un límite de 100 eventos es cobertura.
- CPU individual >7 ms, `exceededCpu`, HTTP 1102 u otro fallo impiden aprobar;
  campos ausentes, eventos faltantes o asociación ambigua producen resultado
  incompleto y suspensión. No extraer CPU de wall time ni de percentiles.
- Emitir solo evidencia saneada y diagnóstico. **Nunca reanudar automáticamente**
  una automatización suspendida por recibir un fichero manual.

El hook actual de `scripts/fdci-automation.mjs` mide antes de su reporte final:
no cubre el último control. Contar muestras sin correlación tampoco demuestra
completitud. Por ello no corresponde conectar una exportación parcial al hook
y habilitar repeticiones. Un piloto supervisado debe terminar cerrado/suspendido
antes de recolectar el conjunto final, incluido cierre/reporte, y solo después
decidir cualquier recuperación bajo autorización separada.

## Alternativa mínima: canary finito supervisado, sin repeticiones

**Preparación condicional, no autorización de ejecución:**

1. Usar exclusivamente el gateway/D1 canary identificados. Si no está habilitada
   la recolección, solicitar autorización específica para configurar Invocation
   Logs allí, con muestreo 1 durante una ventana breve. No cambiar producción,
   plan ni credenciales para intentar resolver la captura.
2. Antes de autorizar una importación, demostrar desde el Dashboard que la
   configuración está activa y que se puede leer un evento individual con CPU.
   Una eventual solicitud de control para comprobarlo necesita autorización:
   no se generó en esta etapa.
3. Si se prueba la automatización nueva, 0033 y el despliegue canary también
   requieren autorización aparte. Usar datos ficticios, dos publicaciones máximo,
   una única corrida, ventana absoluta breve, TTL <=600, sin schedule ni reintentos.
4. Mantener la suspensión por falta de métricas; no quitar el umbral de 7 ms.
   Un dueño observa la prueba; al terminar, cierre total incluido flag automático,
   cero concesiones vigentes y estado HALTED. No reconocer el incidente en el
   freno de historial ni recuperar para permitir una segunda ejecución automática.
5. Exportar el conjunto completo de eventos y conciliarlo con el manifest. Si
   faltan eventos/CPU o no hay margen, dejar suspendido y terminar el piloto.

Esto permite evaluar una corrida con supervisión sin fingir resuelto el lector
desatendido. Tail Workers es de Paid/Enterprise; no se propone como servicio
gratuito ni se incorpora otro servicio. Nada de lo anterior se ejecutó ahora.
