# DocenteTuc 1.2: transición de fuentes (preparación, no activada)

## Escritura elegida

El receptor Worker con exclusión superó 10 ms de CPU en la prueba real. No usarlo
para activar 1.2. El piloto alternativo ejecuta los validadores actuales en Node
y envía consultas parametrizadas a la API REST de D1. Cada publicación se aplica
con `INSERT ... ON CONFLICT` condicionado por hash; un reintento no duplica filas.
La API de D1 devuelve `rows_read` y `rows_written`, que el ejecutor registra sin
imprimir contenidos ni credenciales. No hay reconciliación de ausencias en los
importadores externos ni generación de notificaciones en esta fase.

**No está aprobado para producción aún.** Antes se necesita un token D1 Write
limitado a la base *aislada* para comprobar la API REST real con `NULL`, números,
una alta, una repetición, una actualización y un fallo intermedio. El token de
producción, si se autoriza después, debe limitarse a `docentetuc-db`, expirar,
guardarse solo en un environment protegido de GitHub y rotarse tras incidentes.
Ese permiso permite SQL arbitrario dentro de la base: la protección de la rama,
SHA fijado, revisión del workflow y monitor de cuotas son imprescindibles. No
existe una credencial D1 con permisos solo sobre `publications`.

La operación de un registro es idempotente. Las varias operaciones de estado se
ejecutan secuencialmente: **no se presume transacción REST**. Si falla una,
el job falla y puede repetirse; `last_successful_sync_at` se establece solo al
terminar el recorrido verificado. Una importación puntual FDCI no marca todo
el catálogo como sincronizado.

## Corte de escritores, por fuente

`EXTERNAL_SYNC_SOURCES` acepta `FDCI,SIME,JUNTAS,CENET,INFD`. Al activarse para
una fuente, `/api/sync` omite su recolector, sus filas del catálogo, sus estados
de salud y su reconciliación; no debe marcarla retirada por una respuesta parcial.
`FDCI_SYNC_MODE=external` conserva el corte FDCI anterior. Por defecto todos
los recolectores legacy siguen activos. Los importadores externos permanecen
manuales y apuntan a entornos de prueba.

Transición para **una** fuente: (1) fijar SHA y registrar versión y configuración
del Worker actual; (2) desplegar el código nuevo con todos los flags aún en modo
legacy; (3) suspender temporalmente el disparador antiguo durante una ventana
controlada, o demostrar mediante registros que no queda ninguna invocación
antigua en curso; (4) esperar su terminación verificable —el nuevo flag no
protege invocaciones iniciadas antes—; (5) habilitar el flag de esa fuente,
confirmar que una ejecución nueva la omite y que las demás siguen; (6) ejecutar
**una** importación externa; (7) verificar fila, fechas, enlace, salud, cuotas,
CPU web y ausencia de duplicados; (8) reanudar el disparador sin importar de
nuevo esa fuente. Si no se puede verificar el drenaje, no importar. El retraso
temporal de retención/push durante la suspensión debe comunicarse; no se borran
publicaciones. Reversión: detener job externo, esperar su finalización, volver a
legacy y restaurar la versión Worker previa si es necesario. Nunca revertir D1.

## Workflows y fuentes

Los cinco workflows existentes siguen `workflow_dispatch` únicamente, con
concurrencia por fuente. No se agrega `schedule` hasta aprobar el mecanismo de
escritura, el corte y un monitoreo de fallos. Frecuencias iniciales propuestas:
FDCI cada hora; SIME cada 30 minutos lunes/martes y cada dos horas el resto;
Juntas cada hora miércoles y cada cuatro horas el resto; CeNET e INFoD cada
seis horas. Evitar el minuto cero, separar minutos por fuente y comparar los
límites diarios de GitHub/D1 antes de activar. Las programaciones de GitHub
pueden atrasarse u omitirse: registrar último intento, último éxito, error y
alertar cuando se supere el umbral de antigüedad de cada fuente. La clave de
Drive para verificar las seis carpetas públicas de Juntas no está disponible
en este entorno; esa comprobación sigue pendiente y no se inventan resultados.

Noticias sigue bajo revisión humana: una publicación oficial es evidencia o
candidata, nunca noticia automática. Exigir fuente verificable, fecha respaldada,
título editorial y enlace antes de publicar; no inferir adjudicaciones desde
comunicados de actos. Notificaciones son una etapa separada: procesar IDs de
publicaciones cambiadas por lotes de perfiles, respetar preferencias y crear
eventos con `INSERT OR IGNORE` y clave de deduplicación; luego enviar push en
lotes independientes. No activar avisos hasta comprobar con perfiles sintéticos
que el circuito completo no duplica ni pierde eventos y no excede D1 Free.
