# DocenteTuc 1.2: transición de fuentes (preparación, no activada)

## Escritura elegida

El receptor Worker con exclusión superó 10 ms de CPU en la prueba real. No usarlo
para activar 1.2. El piloto alternativo ejecuta los validadores actuales en Node
y envía consultas parametrizadas a la API REST de D1. Cada publicación se aplica
con `INSERT ... ON CONFLICT` condicionado por hash; un reintento no duplica filas.
La API de D1 devuelve `rows_read` y `rows_written`, que el ejecutor registra sin
imprimir contenidos ni credenciales. No hay reconciliación de ausencias en los
importadores externos. Los avisos y recordatorios externos se prueban con D1
aislada y un proveedor de push simulado. El envío real sigue desactivado.

**No está aprobado para producción aún.** El usuario completó una prueba REST
puntual en la D1 canary `docentetuc-fdci-canary-1-1`: alta, lectura, cambio,
repetición e SQL inválido; informó 7 solicitudes, 4 filas leídas y 6 escritas.
El token temporal fue revocado. Esto valida el transporte, no una importación
completa ni la seguridad de una credencial productiva.
Cloudflare documenta
recursos de token por cuenta, zona o usuario, no un recurso individual por base
D1. El UUID de la base en la URL elige el destino pero no limita el permiso.
No se debe asumir que un token D1 Write de la cuenta productiva pueda restringirse
a `docentetuc-db` ni a la tabla `publications`: podría ejecutar SQL arbitrario
en las D1 accesibles de esa cuenta. Antes de decidir una credencial productiva
se deben verificar `NULL`, números, alta, repetición, actualización, fallos y
métricas en la D1 canary; luego evaluar explícitamente el riesgo de cuenta,
expiración, environment protegido, SHA fijado y monitor de cuotas. La sonda
`scripts/probe-d1-rest-canary.mjs` fija la UUID canary en código, rechaza una
UUID por variable de entorno, comprueba por API el nombre y UUID antes de
escribir y usa solo una tabla sintética dedicada. Es una protección ante errores
de configuración del ejecutor, **no** reduce el permiso del token: si se filtra,
podría acceder también a D1 productiva. Para la prueba, limitar el token a la IP
local de salida y a una caducidad corta; no guardarlo en GitHub ni en el
repositorio. Usar solo variable local temporal y revocarlo al terminar.

La operación de un registro es idempotente. Las varias operaciones de estado se
ejecutan secuencialmente: **no se presume transacción REST**. Si falla una,
el job falla y puede repetirse; `last_successful_sync_at` se establece solo al
terminar el recorrido verificado. Una importación puntual FDCI no marca todo
el catálogo como sincronizado.
Para SIME, Juntas, CeNET e INFoD, Node lee únicamente IDs, hashes y estado de
retiro de la fuente en páginas de 200; las filas sin cambios no disparan una
lectura D1 individual. No se cargan perfiles ni datos privados para importar.

## Corte de escritores, por fuente

`EXTERNAL_SYNC_SOURCES` acepta `FDCI,SIME,JUNTAS,CENET,INFD`. Al activarse para
una fuente, `/api/sync` omite su recolector, sus filas del catálogo, sus estados
de salud y su reconciliación; no debe marcarla retirada por una respuesta parcial.
`FDCI_SYNC_MODE=external` conserva el corte FDCI anterior. Por defecto todos
los recolectores legacy siguen activos. Los importadores externos permanecen
manuales y apuntan a entornos de prueba.

Transición para **una** fuente: (1) fijar SHA y registrar versión y configuración
del Worker actual; (2) desplegar el código nuevo con todos los flags aún en modo
legacy; (3) suspender temporalmente el disparador antiguo durante una ventana
controlada, o demostrar mediante registros que no queda ninguna invocación
antigua en curso; (4) esperar su terminación verificable —el nuevo flag no
protege invocaciones iniciadas antes—; (5) habilitar el flag de esa fuente,
confirmar que una ejecución nueva la omite y que las demás siguen; (6) ejecutar
**una** importación externa; (7) verificar fila, fechas, enlace, salud, cuotas,
CPU web y ausencia de duplicados; (8) reanudar el disparador sin importar de
nuevo esa fuente. Si no se puede verificar el drenaje, no importar. El retraso
temporal de retención/push durante la suspensión debe comunicarse; no se borran
publicaciones. Reversión: detener job externo, esperar su finalización, volver a
legacy y restaurar la versión Worker previa si es necesario. Nunca revertir D1.

## Workflows y fuentes

Los cinco workflows existentes siguen `workflow_dispatch` únicamente, con
concurrencia por fuente. Usan el ejecutor Node/REST, fijado por SHA y bloqueado
en código a la UUID y nombre canary; no aceptan una UUID de entorno. Requieren
un secreto `D1_IMPORT_TOKEN` que no está configurado y no deben ejecutarse aún.
Sus cron propuestos son comentarios, no disparadores. Para producción se requiere
otro cambio revisado de destino, credencial, corte y monitoreo, con autorización
separada. No se agrega `schedule` hasta entonces. Frecuencias iniciales propuestas:
FDCI cada hora; SIME cada 30 minutos lunes/martes y cada dos horas el resto;
Juntas cada hora miércoles y cada cuatro horas el resto; CeNET e INFoD cada
seis horas. Evitar el minuto cero, separar minutos por fuente y comparar los
límites diarios de GitHub/D1 antes de activar. Las programaciones de GitHub
pueden atrasarse u omitirse: registrar último intento, último éxito, error y
alertar cuando se supere el umbral de antigüedad de cada fuente. La clave de
Drive para verificar las seis carpetas públicas de Juntas no está disponible
en este entorno; esa comprobación sigue pendiente y no se inventan resultados.

Los runners estándar de GitHub no tienen IP de salida fija. El token temporal
restringido a la IP doméstica sirvió para la sonda local, pero no es una
configuración directamente reutilizable para ejecuciones automáticas. Antes de
guardar un token de cuenta en GitHub se requiere una decisión explícita sobre
ese permiso amplio y sus controles; aún no hay secreto REST.

Noticias sigue bajo revisión humana: una publicación oficial es evidencia o
candidata, nunca noticia automática. Exigir fuente verificable, fecha respaldada,
título editorial y enlace antes de publicar; no inferir adjudicaciones desde
comunicados de actos. Los avisos por publicaciones cambiadas y los recordatorios
de capacitación, designación, Agenda y eventos manuales se materializan por lotes
con deduplicación. Una prueba local conecta estos últimos al despachador con
preferencias y proveedor simulado. No activar push real hasta validar transporte,
cuotas y exclusión en un entorno aislado.
La prueba local recibe eventos `created`/`updated` explícitos. Falta conectar
los cambios confirmados por REST a un registro duradero de eventos para que una
interrupción entre importación y materialización no pierda avisos; no basta con
los contadores de publicaciones. No activar avisos externos automáticamente
hasta resolver este punto y verificar una entrega real a un dispositivo de prueba.

## Sonda REST canary: ejecutada una vez; no repetir sin autorización

Para una eventual repetición autorizada, crear un token temporal D1 Edit en la cuenta
actual, limitado a la IP pública de salida y con caducidad corta. El permiso
abarca la cuenta, no solo la canary. En PowerShell, desde el repositorio:

```powershell
$env:CF_ACCOUNT_ID = Read-Host 'Cloudflare account ID'
$secureToken = Read-Host 'Token D1 Edit temporal' -AsSecureString
$tokenPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secureToken)
try {
  $env:D1_CANARY_TOKEN = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($tokenPointer)
  $env:D1_REST_CANARY_PROBE = 'true'
  Remove-Item Env:D1_DATABASE_ID -ErrorAction SilentlyContinue
  node .\scripts\probe-d1-rest-canary.mjs
} finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($tokenPointer)
  Remove-Item Env:D1_CANARY_TOKEN,Env:D1_REST_CANARY_PROBE -ErrorAction SilentlyContinue
}
```

La sonda fija y verifica la UUID y nombre canary, prueba alta, lectura,
actualización, repetición y error con datos sintéticos, y registra consultas y
filas. Detenerse ante una identidad distinta; no probar otra UUID. Revocar
inmediatamente el token desde Cloudflare y confirmar que quedó inactivo. No
guardarlo en GitHub, archivos ni historial de comandos.

El build sin secretos ni despliegue está preparado en
`.github/workflows/build-1.2-linux.yml`. Como GitHub solo habilita un
`workflow_dispatch` si el archivo existe en la rama predeterminada, el build
puede dispararse por `push` **solo** de `feat/1.2-sync-integration`, sin tocar
la rama predeterminada ni activar los importadores.
