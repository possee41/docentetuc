## Mecanismo y alcance

Se reutilizan `.github/workflows/notices-reminders.yml`,
`scripts/reminders-worker.mjs` y el Worker `docentetuc-notices-1-2`.
Actions hace **una sola llamada HTTP**; el Worker ejecuta el materializador
existente. No se agrega Cron al Worker ni se toca la retención de la web.
El runner no recibe SQL ni tokens Cloudflare/D1.

Antes, el runner/workflow permitían diez registros y no bloqueaban futuras
llamadas después de una respuesta incierta. Ahora:

- Runner: por defecto dos, únicamente uno o dos; schedule futuro siempre dos.
  El Worker mantiene su API validada (hasta diez): **esta automatización**
  nunca solicita más de dos; no habilitar otros clientes con el mismo secreto.
- Una ejecución a la vez, grupo `notices-reminders`, sin cancelar la activa.
- Variable de repositorio `NOTICES_AUTOMATION_ENABLED=true` obligatoria;
  ausente o distinta de `true` implica apagado. El script también la comprueba.
- SHA aprobado `NOTICES_REF`, checkout exacto, sin credenciales Git persistidas.
- Un único intento, timeout de 20 s, sin seguir redirecciones. Nunca reintenta
  la llamada tras 503, desconexión, timeout, JSON inválido o ACK inconsistente.
- ACK mantiene su significado. El runner valida enteros, límites y
  `processed == considered`. Una carrera que deje flags ya confirmados puede
  ser inocua, pero un ACK incompleto exige revisión y detiene la automatización.
- Historial de Actions: el último run previo no omitido debe estar terminado
  y exitoso. Fallo/cancelación/timeout/estado incierto bloquea llamadas futuras.
  Un rerun también requiere revisión. Si falta historial suficiente o su API
  falla, se detiene antes de llamar al Worker. Lee como máximo cien runs.
  Un operador puede liberar el bloqueo **solo con un dispatch manual** y
  `acknowledge_failure=true`, tras conciliar D1. No borra datos ni reenvía nada.
- Resultado mínimo: ACK, inicio UTC y tiempo transcurrido. `cpuTimeMs:null` y
  `d1:null` porque el endpoint no expone esas métricas. Nunca confundir latencia
  con CPU. Los errores registrados son códigos fijos, sin cuerpo ni secretos.

Se conservan dedupe keys, índices únicos, flags y batch atómico D1. Si se pierde
el ACK después de confirmar el batch, se consulta el estado antes de autorizar
otra llamada. No se promete exactamente una ejecución HTTP.

**Límite funcional existente:** capacitaciones, designaciones y publicaciones
guardadas generan filas en `notifications`. Los eventos manuales generan
`manual_event_push_queue` y actualizan su flag/recurrencia. Esa cola no aparece
en la consulta de notificaciones internas de `/api/app`; con push desactivado,
no entrega un aviso al usuario. La Agenda sigue mostrando el evento. Esta
preparación no cambia esa semántica ni habilita despacho. No declarar resuelto
el aviso interno de eventos manuales; requiere una decisión/corrección acotada
antes de anunciar cobertura completa de todos los tipos de Agenda.

## Frecuencia y presupuesto inicial propuestos

**Dos registros una vez por hora**, minuto UTC 17 (`17 * * * *`). El schedule
está únicamente comentado, no activo. Máximo teórico 48 registros por día si
no hay fallos, retrasos ni ejecuciones omitidas. Las cuatro fuentes conservan
su prioridad actual: capacitación, designación, guardado y evento manual.
Una cola sostenida de un tipo anterior puede retrasar los siguientes; sin
medir la demanda real no se garantiza tiempo de vaciado ni ausencia de espera.

No hay bucle para vaciar pendientes. Un backlog queda para la siguiente hora.
Un evento recurrente atrasado avanza una ocurrencia por procesamiento, según
la lógica existente. Los avisos pueden llegar tarde respecto a la hora pedida;
Actions puede retrasar u omitir ejecuciones y no es un programador puntual.

Sin pendientes se hace una sola llamada y ACK 0/0/0, sin escrituras: por lectura
del código son cinco SELECT (identidad más cuatro tipos). Con hasta dos casos,
como máximo cinco SELECT y cuatro sentencias de escritura en un batch: hasta
seis cruces D1, **no seis sentencias SQL**. Esto no mide filas leídas: las
consultas de elegibilidad aún pueden recorrer históricos. No se usa como
garantía de cuotas con volumen productivo desconocido.

24 jobs diarios son aproximadamente 720 minutos/30 días si cada job Linux
facturase un minuto; dos minutos serían 1440. Estimación, no consumo medido ni
confirmación del saldo gratuito. Revisar Billing/Actions y compartir presupuesto
con importadores antes de habilitar. No instalar dependencias en este workflow.

CPU conocida: **7,545 ms en una sola invocación canary**, límite HTTP Free de
10 ms confirmado previamente. No demuestra margen sostenido ni se extrapola
a producción. Menor frecuencia reduce costo diario, **no CPU por invocación**.
Un 1102/503 bloquea llamadas posteriores, pero un HTTP 200 no informa CPU.
Revisar Logs/Analytics existentes del piloto: ante recursos excedidos, error
D1, ACK anómalo o CPU >=10 ms, apagar; si la CPU supera el margen preventivo
de 7 ms, no ampliar ni dejar sin supervisión. La muestra 7,545 ya supera ese
margen: hace falta aceptación explícita del riesgo para un piloto horario,
no está demostrada una operación Free automática estable.
