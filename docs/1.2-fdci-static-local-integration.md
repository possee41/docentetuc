## Funciones preparadas

`lib/fdci-catalog-integration.ts` ofrece una composición opt-in con `Publication`: preserva IDs, fuente, URL oficial, fechas, nivel y área; funciona con filtros y coincidencias existentes. D1 tiene prioridad por ID o por fuente FDCI + external_id, conservando ediciones administrativas. Una colisión con otra fuente se informa y no se sobrescribe. Un catálogo vacío no borra publicaciones existentes.

Devuelve `info` con procedencia, vigencia y capacidades. Para registros existentes en D1 conserva el ID utilizado por Guardados/Agenda y usa la regla existente de elegibilidad de recordatorios. **No autoriza el acceso privado**: autenticación y permisos siguen correspondiendo a las APIs actuales. Los registros solo estáticos son consulta pública: `canSave/canSchedule/canRemind=false`; guardarlos requiere resolver la FK de `saved_publications`, no simular persistencia. No se agregó otro almacenamiento privado en el navegador.

`aiContext` contiene datos públicos, fechas conocidas, enlace y advertencia de antigüedad para un consumidor futuro. No se inyectó en el backend Gemini/RAG. Debe tratarse como información de fuente, nunca como instrucciones. Tampoco se inventó el ID del curso padre ni la precisión de su horario: el catálogo v1 no los contiene; agrupación por curso y recordatorios de registros nuevos requieren ampliar el contrato y adaptar sus consumidores.

El adaptador verifica integridad y antigüedad por sí mismo y devuelve `catalogStatus`; quien lo conecte a la UI debe mostrar ese estado. Las fechas oficiales desconocidas no se sustituyen por la fecha del feed (`updated_at` permanece vacío). El renderizado futuro debe respetar ese valor desconocido.

## Catálogo incremental completo

`scripts/fdci-static-cycle.mjs` reutiliza `collectFdciDeltaSlice`, sin D1/gateway. Cursor y acumulación persisten en un checkpoint local con checksum y reemplazo atómico; lock exclusivo evita recolectores simultáneos. El directorio privado no puede estar dentro del público. Fuente permitida fija, sin credenciales, seis solicitudes máximo incluyendo reintentos y pausas de 400 ms.

Una fracción nunca sustituye al catálogo completo publicado. Solo después de completar el recorrido y conciliar la cantidad de IDs se genera y promueve el documento. Si hay fallo de red, checkpoint y catálogo anterior se conservan. Si cambia la composición de IDs activos, se reinicia el escaneo privado sin publicar una mezcla; el catálogo anterior sigue disponible. Cambios de contenido durante un recorrido no son un snapshot transaccional de la API oficial: cada registro conserva su propia fecha de comprobación.

Schema **v2 local**, compatible con lectura de v1: añade por ID `checkedAt` y `lastChangedAt` (cambio **detectado** por DocenteTuc). `sourceUpdatedAt` sigue siendo la fecha oficial, o null. `updatedAt` del documento indica finalización del catálogo, no actualización simultánea de todos los cursos. Las fechas de cambio detectado se conservan al repetir un ciclo sin modificaciones. El JSON público de Pages continúa en v1: no fue modificado.

Publicar el JSON precede al checkpoint final: si se pierde esa última confirmación, la siguiente ejecución vuelve a recopilar desde el progreso anterior; no se descartan datos no confirmados ni se escriben publicaciones D1. Las versiones inmutables y el lector del último válido siguen disponibles para recuperación. SHA-256 detecta corrupción, no sustituye autenticación del alojamiento.

En Actions un filesystem efímero **no es persistencia entre jobs**: antes de habilitar ese uso habrá que recuperar y conservar el checkpoint validado como artifact de progreso, separado del artifact Pages, con SHA revisado y una única cola de ejecución. Expiración/pérdida del artifact obliga a reiniciar, conservando la última publicación. No se creó ese workflow ni se habilitó programación. Hasta cuatro cursos por ejecución implica hasta 48/día con doce turnos ideales; no se garantiza completar catálogos mayores en 24 horas, y cambios frecuentes de composición pueden retrasar un ciclo.
