# Prueba canary del despacho push de DocenteTuc 1.2

**Estado: Worker y D1 canary existentes; `500-dense` ya se invocó, con CPU pendiente.**
El Worker [push-canary.mjs](../workers/push-canary.mjs) importa el
`dispatchPushNotifications` real. Su proveedor inyectado siempre devuelve
HTTP 201 localmente y nunca llama a un proveedor push. No tiene VAPID real,
Cron, rutas personalizadas, assets web ni acceso a datos de docentes.

## Recursos y autorización pendiente

- Worker canary existente: `docentetuc-push-canary-1-2`, solo en `workers.dev`.
- D1 canary existente: `docentetuc-push-canary-1-2`, con el esquema sintético de
  [push-canary-schema.sql](../scripts/push-canary-schema.sql).
- Un secreto temporal exclusivo `CANARY_BEARER_TOKEN`, ingresado localmente;
  ninguna credencial productiva ni VAPID.
- Workers Logs con 100 % de invocation logs para leer `$workers.cpuTimeMs`,
  `$workers.wallTimeMs` y `$workers.outcome`. El Worker registra solo escenario,
  identificador técnico, resultados y métricas D1; nunca endpoints ni secretos.

El Worker y la D1 canary ya existen. Cualquier nueva escritura o invocación
remota **requiere autorización posterior**. Antes de crear recursos adicionales,
comprobar que queda un cupo de D1 Free y margen diario de filas en la cuenta.
La configuración local tiene la UUID de la D1 canary; conservarla solo en ese
archivo local, fuera del commit. El preflight
también rechaza la UUID productiva conocida, otras rutas, Cron, assets,
bindings o variables que no sean `CANARY_BUILD_ID`. El propio Worker exige
la marca de identidad dentro de D1 antes de cualquier despacho.

El benchmark local existente, con D1 efímera y envío simulado, produjo:

| Pendientes | Escasas: consultas / leídas / escritas | Densas: consultas / leídas / escritas |
| ---: | --- | --- |
| 0 | 2 / 2 / 0 | 2 / 2 / 0 |
| 100 | 10 / 210 / 14 | 10 / 14 / 14 |

Entre 100 y 500 avisos escasos, Cloudflare leyó 801 filas adicionales por
400 avisos adicionales: aproximadamente dos lecturas por aviso. El benchmark
local creció 800 filas en el mismo intervalo. Si esa relación continuara,
1000 escasos rondaría 2013 filas leídas **por invocación**; es una proyección,
no una medición de Cloudflare. Con 288 invocaciones diarias idénticas serían
aproximadamente 580 mil filas leídas antes de sumar cualquier otra carga. No
se usa esa proyección para aprobar una frecuencia productiva.

El canary suma una consulta de identidad D1 a las cifras locales del
despachador. `EXPLAIN QUERY PLAN` usa `idx_notifications_scheduled`, busca la
publicación por ID y después `idx_push_subscriptions_user`; por eso, con dos
suscripciones al final, las lecturas crecen con los avisos pendientes. Las
duraciones del benchmark local incluyen IPC de Miniflare y no representan
CPU Cloudflare. Sin una reducción de CPU demostrada, no se cambia la consulta.

## Próximas pruebas propuestas: densidad y 1000 avisos

**No ejecutar todavía.** Tras completar CPU y outcome de round-7, la siguiente
prueba propuesta es `1000-sparse` para medir el crecimiento de lecturas;
`1000-dense` solo si ambas conservan margen. Cada semilla sustituye el
escenario anterior en la D1 canary y solo contiene datos sintéticos. No hay
cambios de SQL ni despliegue.

Antes de cada caso: confirmar configuración, URL `workers.dev` y secreto
canary sin imprimirlos; generar la semilla de ese caso y aplicarla únicamente
a D1 canary. El [ejecutor local](../scripts/run-push-canary.mjs) reemplaza la
secuencia manual de abajo para casos futuros. Para el **siguiente caso,
`1000-sparse`**, los comandos manuales equivalentes serían:
PowerShell serían:

```powershell
node .\scripts\check-push-canary-config.mjs .\wrangler.push-canary.json
New-Item -ItemType Directory -Force .\outputs | Out-Null
node .\scripts\generate-push-canary-sql.mjs --count=1000 --density=sparse --output=.\outputs\push-canary-seed.sql
npx wrangler d1 execute DB --config .\wrangler.push-canary.json --remote --file .\outputs\push-canary-seed.sql
$headers = @{ Authorization = "Bearer $env:PUSH_CANARY_TOKEN" }
Invoke-RestMethod -Method Post -Uri "$pushCanaryUrl/run/1000-sparse/<nuevo-id>" -Headers $headers
```

Para `1000-dense`, cambiar `--density`, el tramo de URL y el ID.
Anotar `isolateId` e `isolateInvocation` junto con CPU, wall y outcome de
Workers Logs para cada caso. Una invocación posterior en el mismo isolate es
caliente; la primera observada de un isolate nuevo es solo **candidata fría**.
Si no aparece otro isolate de manera natural, dejar pendiente la comparación
fría en vez de forzar un despliegue. Para comparar caliente con caliente sin
duplicados, usar semillas equivalentes y registrar que el isolate sea el
mismo. La repetición inmediata sin resetear debe producir cero envíos y
medirá otro trabajo; no sustituye una repetición del despacho de dos avisos.

**Detenerse sin avanzar al siguiente caso** si la CPU supera 7 ms,
aparece `exceededCpu`, HTTP 1102, un error D1 o un resultado distinto de dos
entregas simuladas sin fallos. Un resultado aislado bajo 7 ms no habilita el
despacho productivo: hay que comparar primeras invocaciones y calientes de
igual escenario, y reservar cuota D1 y CPU para el tráfico normal.

### Ejecutor de un escenario

Una vez autorizada **esa ejecución individual**, con las variables de entorno
`CLOUDFLARE_ACCOUNT_ID`, `PUSH_CANARY_WORKERS_SUBDOMAIN`,
`PUSH_CANARY_TOKEN` y `PUSH_CANARY_READ_TOKEN` ya cargadas en PowerShell, el
comando único es:

```powershell
node .\scripts\run-push-canary.mjs --scenario=1000-sparse
```

Admite solo `500-dense`, `1000-sparse` y `1000-dense`. Primero valida la
configuración local y consulta **en modo lectura** el subdominio de la cuenta,
los bindings y disponibilidad del Worker, nombre/UUID/marca D1 y su despliegue.
El token `PUSH_CANARY_READ_TOKEN` necesita `Workers Scripts Read` para esas
lecturas de metadatos; es distinto del secreto de acceso al Worker. Si falta
o no tiene permiso, el script se detiene antes de sembrar o invocar. Wrangler
debe tener autorización para operar **solo la D1 canary** en esta prueba.

Después muestra el escenario, la URL canary construida y un `runId` nuevo.
Exige escribir exactamente `EJECUTAR <escenario> <runId>` antes de una única
semilla remota y una única solicitud. No selecciona automáticamente otro
escenario. La semilla contiene un guard de identidad D1. El script guarda
JSON y Markdown en `outputs/`, sin credenciales ni endpoints de suscripciones.

La [API oficial de consulta de Workers Observability](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/)
documenta `Workers Observability Write` para consultar CPU, aunque la interfaz
permite lectura de logs con roles de solo lectura. No se usa ese permiso de
escritura ni se amplían credenciales. El ejecutor solicita ingresar
manualmente `cpuTimeMs` y `outcome` del log exacto identificado por `runId`.
Si faltan, emite `STOP` y `CPU_LOG_REQUIRED` o `OUTCOME_LOG_REQUIRED`. Nunca
trata `wallMs` como CPU ni aprueba el caso por una respuesta HTTP 200 sola.

## Reconstrucción de recursos, solo si se autoriza por separado

Desde PowerShell, en la raíz de esta rama:

```powershell
# Confirmar primero plan, cupos y que la cuenta seleccionada sea la prevista.
npx wrangler d1 create docentetuc-push-canary-1-2
# Copiar la UUID devuelta a wrangler.push-canary.json. No usar otra base.
node .\scripts\check-push-canary-config.mjs .\wrangler.push-canary.json
npx wrangler d1 list
npx wrangler d1 execute DB --config .\wrangler.push-canary.json --remote --file .\scripts\push-canary-schema.sql
npx wrangler deploy --config .\wrangler.push-canary.json
```

Después, crear **solo el secreto de esta prueba** sin imprimirlo:

```powershell
$bytes = [byte[]]::new(32)
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
$env:PUSH_CANARY_TOKEN = [Convert]::ToBase64String($bytes).TrimEnd('=').Replace('+','-').Replace('/','_')
$env:PUSH_CANARY_TOKEN | npx wrangler secret put CANARY_BEARER_TOKEN --config .\wrangler.push-canary.json
```

Obtener la URL `workers.dev` del despliegue y guardarla en
`$pushCanaryUrl`. Comprobar que no sea `docentetuc.com.ar` ni la URL del Worker
principal. Para cada combinación de `0`, `100`, `500`, `1000` y `dense` o
`sparse`, generar y aplicar **solo a la D1 canary** un archivo nuevo:

```powershell
node .\scripts\check-push-canary-config.mjs .\wrangler.push-canary.json
New-Item -ItemType Directory -Force .\outputs | Out-Null
node .\scripts\generate-push-canary-sql.mjs --count=500 --density=sparse --output=.\outputs\push-canary-seed.sql
npx wrangler d1 execute DB --config .\wrangler.push-canary.json --remote --file .\outputs\push-canary-seed.sql
```

El generador sitúa una ventana de silencio de una hora a seis horas del
momento de preparación. Ejecutar las invocaciones enseguida; si transcurren
varias horas, regenerar la semilla para no medir un despacho diferido por
horario silencioso. Los dos usuarios suscritos del caso `sparse` están al
final del catálogo. Los avisos y endpoints son totalmente sintéticos.

Solo si se autoriza **otro despliegue canary** para estudiar arranque,
cambiar `CANARY_BUILD_ID` a un valor breve distinto y redesplegar **solo este
Worker**, luego verificar que la respuesta indique `isolateInvocation: 1`.
La primera respuesta tras un despliegue no garantiza por sí sola un isolate
frío. Anotar `isolateId`; solo clasificar una petición posterior como caliente
si conserva ese identificador y su contador aumenta. Antes de repetir el
mismo escenario, resetear solo las entregas simuladas:

```powershell
# Ejemplo: sustituir la URL y el ID de corrida por los valores de esta prueba.
$pushCanaryUrl = '<URL-workers.dev-verificada>'
$headers = @{ Authorization = "Bearer $env:PUSH_CANARY_TOKEN" }
Invoke-RestMethod -Method Post -Uri "$pushCanaryUrl/run/500-sparse/round-1" -Headers $headers
node .\scripts\generate-push-canary-sql.mjs --reset --output=.\outputs\push-canary-reset.sql
npx wrangler d1 execute DB --config .\wrangler.push-canary.json --remote --file .\outputs\push-canary-reset.sql
Invoke-RestMethod -Method Post -Uri "$pushCanaryUrl/run/500-sparse/round-2" -Headers $headers
```

Hacer la petición sin `Authorization` **después** de medir la primera
invocación autorizada y confirmar HTTP 401 y cero escrituras. Así la prueba
de autenticación no precalienta el isolate antes de la medición fría. No
registrar el valor del token ni encabezados. La respuesta
autorizada muestra `result`, `d1.queries`, `d1.rowsRead`, `d1.rowsWritten`,
`wallMs`, `isolateId` e `isolateInvocation`; `wallMs` **no es CPU**.

En Cloudflare, abrir **Workers & Pages → docentetuc-push-canary-1-2 →
Observability → Logs**. Filtrar por nombre de Worker, hora e ID de corrida.
Anotar por invocación `$workers.cpuTimeMs`, `$workers.wallTimeMs`,
`$workers.outcome`, HTTP y el log `push_canary`. Buscar expresamente
`exceededCpu` y HTTP 1102, incluidos casos sin respuesta del Worker. El campo
de CPU del log de invocación es la evidencia de Cloudflare; el CPU muestreado
por CDP local no lo reemplaza.

Comparar `0` con `100-dense` y `1000-dense`, siempre separando primeras
invocaciones de invocaciones posteriores del mismo isolate. Un pico solo en
la primera invocación con entregas sería **compatible** con el costo de
inicializar la conversión horaria de `isQuietTime`, pero el CPU total no
atribuye ese pico a una función concreta. Si esa distinción es decisiva,
conservar el perfil Workerd ya obtenido como evidencia de atribución y usar
Cloudflare únicamente para confirmar el costo total por invocación. No
interpretar diferencias de `wallMs` como diferencias de CPU.

## Criterios de aceptación

- Para cada escenario: primera invocación confirmada por contador e
  invocaciones posteriores en el mismo isolate; como mínimo dos entregas
  simuladas cuando existan suscripciones, cero en el escenario vacío y sin
  duplicados al repetir sin resetear.
- Máximo observado de `cpuTimeMs` **≤ 7 ms** en cada invocación medida, para
  conservar margen frente a los 10 ms de Workers Free. Ningún `exceededCpu`,
  HTTP 1102 ni error D1. Si un caso falla, detener el ensayo.
- Consultas D1 claramente por debajo de 50 por invocación y filas leídas y
  escritas sostenibles frente a las cuotas diarias de la cuenta, dejando
  capacidad para docentes y el resto de la aplicación.
- Preferencias, silencio, recordatorios, reintentos y límite de dos entregas
  conservados. Esta prueba no valida entrega push real.

Si el margen de CPU no se demuestra, mantener bloqueado el push productivo y
evaluar despacho desde Node/GitHub Actions. No activar ese camino aquí.

Al terminar una prueba autorizada, retirar el secreto temporal y eliminar o
desactivar los recursos canary según el plan aprobado; limpiar la variable
local con `Remove-Item Env:PUSH_CANARY_TOKEN`. Ningún paso afecta D1 real.
