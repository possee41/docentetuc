# FDCI: automatización acotada implementada en local

Base `9731c1479105a385665795049dff96c86ef31a9b`. Ninguna operación remota.
No se crearon secretos/entornos ni se activaron Cron, workflows o importadores.
Se aplicó la migración nueva solo en SQLite efímero y D1 local de Miniflare.

## Arquitectura y garantías

Se reutilizan el importador incremental, normalización, receiver, checkpoints,
concesión y SQL con fence existentes. La nueva fachada
`/api/internal/fdci-automation/{identity,start,import,checkpoint,close,finish}`
solo permite operaciones FDCI enumeradas. No hay SQL arbitrario, eliminación de
publicaciones ni API pública de recuperación.

La credencial exclusiva `FDCI_AUTOMATION_SECRET` no se admite en las rutas legacy.
Debe ser diferente del secreto del piloto. `fdci-pilot` y su workflow manual no
se modificaron. El automático usaría `fdci-automation`, rama autorizada, SHA
aprobado completo y propietario `run_id-1`; se rechazan reruns con intento >1.
GitHub no recibe credenciales Cloudflare/D1 ni permisos para cambiar Workers.

El diseño anterior de mantener únicamente el modo lease armado se reforzó:
el requisito nuevo de limitar una credencial comprometida exige una **ventana
absoluta aprobada por el operador**. La tabla nueva `fdci_automation_control`
inicia HALTED, sin ventana ni SHA aprobados. Incluso con un secreto válido y el
flag true, no puede operar sin esa aprobación independiente.

La ventana empieza en un límite UTC de dos horas y dura como máximo **24 horas**.
Solo un propietario puede usar cada turno UTC de dos horas, hasta dos intentos
de publicación por concesión y como máximo 600 segundos; el vencimiento se
recorta al fin absoluto autorizado. Repetir start con el mismo propietario no
extiende el vencimiento; close no permite reutilizar el turno. Una nueva ventana
no puede aprobarse con la credencial automática. Esto prepara un **piloto finito**,
no un servicio indefinido sin intervención del dueño.

El plano legacy puede conservar sus cuatro flags cerrados. Solo la fachada
autenticada crea un contexto interno FDCI con lease obligatorio; no altera env
remota, no despliega versiones y no habilita otras fuentes. Su flag adicional es
`FDCI_AUTOMATION_ENABLED`, deshabilitado por defecto si falta. No llamar a ese
servicio "cerrado totalmente" cuando el flag automático está true: el control
autenticado está disponible dentro de la ventana; las escrituras necesitan lease.

El límite FDCI de TTL >600 se **rechaza**, no se recorta silenciosamente, también
en el control legacy. Las otras fuentes mantienen su comportamiento previo.
La fachada además impone en servidor el límite de dos intentos: un tercer envío
suspende. Cuenta también un reenvío sin cambios, por seguridad ante credenciales
comprometidas. La restricción de seis solicitudes oficiales y pausa de 400 ms
permanece en el runner aprobado: el gateway no puede controlar solicitudes que
un atacante haga por su cuenta a un sitio externo.

El SHA en la cabecera se compara con la aprobación persistida y el runner comprueba
su HEAD, pero no es atestación de GitHub: quien robe el secreto puede copiar ese
SHA y falsificar contenido FDCI dentro de los límites. No puede modificar la
ventana, las fuentes autorizadas, el estado de recuperación, eliminar históricos
ni ampliar quota/TTL. Proteger rama y secretos y revocar una clave comprometida
siguen siendo necesarios. No se promete prevenir todo daño dentro de la fuente.

## Suspensión y recuperación

`RUNNING` se persiste antes de conceder acceso. Un fallo reportado marca HALTED
y vence la concesión del mismo dueño en un batch. Un proceso muerto/cancelado que
no reporta deja RUNNING; al vencer, ningún negocio puede escribir y la siguiente
petición lo convierte en HALTED en vez de otorgar otra concesión. La expiración y
los fences SQL funcionan sin GitHub, Cron ni supervisor adicional.

La fachada suspende ante fallo del receiver/checkpoint, cuota excedida o fallo D1
durante una ejecución. El runner reporta fuente/autenticación/ACK incierto y errores
HTTP como fallo, sin repetir import/start. Una respuesta perdida del reporte de
fallo no se reintenta: el halt ya persistido o el latch RUNNING cubren el caso.
Si se pierde el ACK del reporte de éxito, se intenta una acción compensatoria de
suspensión, nunca una repetición de publicaciones.

**Límite fundamental:** si D1 está caído antes de registrar RUNNING, no puede
persistirse un halt en esa misma D1. Por eso se implementó también el freno de
historial GitHub con `actions: read`: la siguiente corrida no llega al secreto
del importador si la anterior falló, fue cancelada o no ejecutó inequívocamente
el paso importador. Si GitHub no permite leerlo, falla cerrado. No hay PAT de
escritura ni modificación automática de variables. El primer arranque necesita
`FDCI_AUTOMATION_BOOTSTRAP_SHA`; recuperar un fallo exige reconocer su ID exacto
en `FDCI_AUTOMATION_RECOVERY_RUN_ID`. Ese reconocimiento no cubre errores futuros.

Una petición sin credencial válida **no** pausa a otro propietario: eso sería
un vector de denegación de servicio. Sigue siendo rechazada; el fallo del job
legítimo activa el freno de historial. La recuperación de credenciales/configuración
es una intervención del operador, no un reintento autónomo.

La recuperación persistida requiere una operación D1 del operador autorizada
por separado: comprobar identidad, motivo de suspensión, publicación/cursor y
ausencia de concesión vigente; expirar la concesión propia y cambiar HALTED a
IDLE conservando `last_slot` y cuota. No resetear el turno para repetir el mismo
lote. Si se necesita otra ventana/SHA, aprobarlos expresamente. No restaurar D1
ni modificar publicaciones/cursor para forzar éxito.

## Resultados y CPU

El ACK existente no cambió. La envoltura añade `outcome`:

| Resultado | Interpretación |
|---|---|
| CHANGES | Hubo altas/actualizaciones |
| NO_CHANGES | Examen sin altas/actualizaciones |
| NO_ACTIVE_DATA | Lista activa vacía, sin escritura de publicaciones ni avance |
| PARTIAL_PROGRESS | Progreso limitado esperado; no se afirma catálogo completo |
| FAILED | Fallo/ACK incierto/cierre no confirmado |

Un vacío coherente no falla por sí mismo; apertura y cierre siguen siendo
escrituras legítimas de control. No se actualiza `sync_state` ni el catálogo
histórico y no se generan avisos ni envíos push.

**Bloqueo real pendiente:** hoy no hay un lector remoto autorizado y fiable de
CPU individual (Observability dio 403). Se dejó una entrada de medición explícita
en el runner, usada solo con datos ficticios en pruebas. Exige muestras completas
para las peticiones anteriores al reporte final, CPU finita y outcome ok; >7 ms
o falta de evidencia suspende. No se admite p99 como sustituto.

El CLI no tiene un adaptador real y por tanto **suspende al final de la primera
corrida**, incluso si hubo negocio correcto. No se ha convertido ese bloqueo en
una variable booleana para saltarlo. La llamada final de control tampoco tiene
CPU facturable medida; un fallo de esa llamada queda cubierto por suspensión/latch,
pero no se demuestra un máximo individual para ella. Una política/medición real
completa debe resolverse antes de ofrecer repetición desatendida.

No se midió CPU Cloudflare ni CPU facturable local. Workerd se usó para validar
SQL y atomicidad, no para afirmar cumplimiento de 10 ms. Las nuevas comprobaciones
añaden trabajo: el margen del código anterior no se hereda automáticamente.

## Consumo observado local y estimado

- Adaptador SQLite: **46 cruces tipo RPC** para el caso exitoso de dos publicaciones
  y **18** para el vacío, incluyendo los controles nuevos; el batch cuenta como
  un cruce. Son llamadas del modelo local, no mediciones remotas de D1 ni filas
  físicas. Estimación por lectura del código: alrededor de seis cruces por
  invocación exitosa de escritura unitaria; los fallos suman la suspensión.
  No son 46 consultas en un único Worker.
- Workerd/D1 efímera: alta correcta, repetición con `rowsWritten=0`, tercera
  tentativa rechazada y HALTED persistido. No se hicieron ensayos de carga.
- Con doce oportunidades en una ventana de 24 h: techo operativo de 24 comisiones
  examinadas y 72 solicitudes oficiales; vacío 24 solicitudes. Son estimaciones
  y bajan con pausas, fallos y omisiones del programador.
- Con la política CPU actual, falta de métricas detiene la primera y las demás
  se bloquean: no estimar doce importaciones efectivas como estado operativo.

Apagado independiente de GitHub: **`FDCI_AUTOMATION_ENABLED=false` en Cloudflare**
además de los cuatro flags legacy cerrados. Los cuatro anteriores por sí solos
no deshabilitan la nueva fachada cuando el flag automático está true. El retorno
es 503 antes de D1. Expirar/suspender la concesión propia en D1 requiere autorización
para esa escritura de control; el TTL la vence sin intervención si no es posible.
Un cambio de flags no cancela SQL ya en vuelo; los fences de concesión son el
corte para esas solicitudes.

Después, deshabilitar únicamente el workflow automático/variable en GitHub y
cancelar su corrida si corresponde. No borrar históricos, reiniciar cursor,
restaurar D1 ni reactivar el workflow antiguo. Recuperar solo después de revisión
del operador y reconocimiento del incidente. No dar al runner permisos para esto.

## Dictamen

**APTO CON CONDICIONES para preparar un piloto canary finito; NO APTO todavía
para programación productiva repetida.** La habilitación tiene límites server-side
y la suspensión ya se implementó; no es un gateway permanentemente abierto.
Persisten la falta de lector real de CPU individual, la CPU adicional no medida
y los pasos de publicación/entorno/0033 aún no autorizados. No hay una solución
gratuita demostrada para el monitoreo CPU desatendido con los permisos actuales;
se bloqueó únicamente esa parte en vez de quitar el umbral o ampliar privilegios.

Solo cambios locales en este commit. Se conservaron AGENTS.md,
wrangler.push-canary.json y el informe de escalabilidad ajenos. No se modificaron
Noticias, Administración, SIME, web, secretos ni otros Workers desplegados.
