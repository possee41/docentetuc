# FDCI directo a D1 REST: bloqueo de seguridad

Base: `b2e8598`, que incluye `2a6e766`. Decisión del propietario respetada: Cloudflare Free. Solo se leyeron código local y documentación pública oficial; sin acceso a la cuenta, bases remotas, tokens, despliegues o ensayos. HALTED no se modificó.

## Resultado: NO APTO bajo las garantías actuales

La API REST permite enviar SQL parametrizado y lotes. Técnicamente se podría reutilizar el recolector Node y ejecutar las operaciones existentes por REST, evitando invocar el gateway Worker. Pero desaparece la frontera de autorización que limita al importador: la credencial REST permite enviar SQL directamente, fuera del adaptador.

Evidencia oficial revisada:

- [Permisos Cloudflare](https://developers.cloudflare.com/fundamentals/api/reference/permissions/): D1 Edit/Write se encuentra entre los permisos de cuenta, cuyo scope es `com.cloudflare.api.account`.
- [Recursos y restricciones de tokens](https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/): recursos User, Account y Zone; para Account se selecciona una cuenta o todas. No se documenta un recurso D1 UUID ni una restricción por tabla, sentencia u operación. TTL/IP restringen tiempo/origen, no SQL autorizado.
- [D1 REST query](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/): ruta con account/database ID y cuerpo `{sql, params}` o `{batch}`. Fijar una UUID en Node no convierte esa ruta en una restricción del token. El endpoint admite SQL proporcionado por el portador.

Por tanto, no hay soporte documentado verificado para un token de escritura limitado a una sola D1 y a las operaciones FDCI. No se crearon tokens para probar su alcance. No se recomienda D1 Write de la cuenta productiva en Actions.

## Garantías que no pueden trasladarse solo al runner

| Garantía | Adaptador Node correcto | Portador del token que omite el adaptador |
|---|---|---|
| Fuente y SQL permitidos | Puede limitarse a plantillas parametrizadas | Puede enviar otras sentencias directamente |
| HALTED, SHA y cuota | Puede comprobarlos antes de escribir | Puede modificar o evitar esos controles |
| TTL y propietario | Puede usar fences SQL | Puede emitir escrituras sin esos fences |
| Cursor, hashes, auditoría | Puede mantenerlos consistentemente | Puede alterarlos o borrarlos |
| Cambios administrativos | Puede usar compare-and-swap | Puede sobrescribirlos fuera del contrato |
| Aislamiento D1 | Puede fijar nombre/UUID | El permiso de cuenta no documenta esa misma restricción |

GitHub concurrency, entorno protegido, SHA fijo, secreto temporal y SQL parametrizado reducen accidentes y exposición, pero no limitan lo que Cloudflare acepta del token. Incluso una hipotética restricción a una base no limitaría tablas/operaciones dentro de esa base. Una cuenta separada de pruebas reduce el alcance sobre otras bases, pero no resuelve el bypass de HALTED y los controles de la misma base.

## Atomicidad y recuperación

El contrato REST consultado describe ejecución en batch, pero no se tomó la garantía de rollback de Workers `DB.batch()` como prueba automática del contrato REST. Tampoco se presentaría una transacción SQLite local como demostración de atomicidad remota. No se verificó atomicidad REST en Cloudflare, conforme a la prohibición de acceso remoto.

Un adaptador no debe separar un batch en varias llamadas ni reintentar automáticamente una escritura de resultado incierto. La recuperación requeriría leer estado confirmado y conservar la cola/CAS. Esas propiedades de un cliente correcto no restauran la restricción de privilegios perdida.

## Detención y siguiente paso

Se aplicó la condición expresa del propietario: **si no pueden mantenerse garantías equivalentes, detenerse**. Por eso no se implementó un adaptador de escritura, no se modificó el recolector ni se fabricó una prueba exitosa con un backend simulado. No hay prototipo funcional aprobado ni pruebas nuevas que reportar; las pruebas anteriores no demuestran seguridad de REST directo.

Una futura prueba aislada de REST solo tendría sentido para evaluar su protocolo, bajo una autorización que acepte explícitamente este modelo de confianza diferente: cuenta de ensayo sin recursos reales, datos sintéticos, credencial temporal de mínima duración y verificación independiente de alcance y atomicidad. No habilitaría automáticamente la misma solución en producción ni justificaría un token sobre la cuenta actual.

Para conservar las garantías actuales con D1 central se necesita una frontera de persistencia restringida en servidor (como el gateway), o soporte verificable del proveedor para autorizar únicamente las operaciones necesarias. No se propone contratar Paid, ampliar permisos o activar otra arquitectura como sustitución implícita. Ninguna intervención remota queda autorizada por este informe.
