## Procedimiento coordinado para una futura autorización

No se ejecuta ahora. La documentación de GitHub establece la secuencia normal:
abrir el aviso de revisión, seleccionar el entorno y aprobar. No es necesario
usar el bypass administrativo.
[Referencia oficial](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments).

1. Confirmar que el usuario tiene GitHub abierto, cuenta `possee41`, y está
   disponible. Preparar el cierre independiente; gateway cerrado y sin temporizar
   todavía la ventana de importación.
2. Sólo con nueva autorización, despachar una vez y comunicar inmediatamente
   enlace, número visible **#N**, nombre y Waiting. Mantener gateway cerrado.
3. El usuario entra a Actions → workflow FDCI → **título de la fila #N** con reloj
   amarillo. No al enlace del archivo YAML ni al botón verde Run workflow.
   El texto «manual, disabled» es parte estática del nombre del workflow.
4. En Summary/Resumen, pulsar Review deployments en el aviso de revisión.
   Si no aparece, detener la coordinación y revisar cuenta/página con una captura,
   manteniendo el gateway cerrado. Una corrida cancelada no tiene aprobación pendiente.
5. En el diálogo, **marcar el cuadrado pequeño a la izquierda de `fdci-pilot`**.
   Confirmar check visible y botón Approve and deploy habilitado. El comentario
   puede quedar vacío. No pulsar aprobación todavía.
6. **Sólo cuando el usuario confirme esa pantalla preparada**, armar la ventana
   breve y el supervisor independiente. La concesión no se abre manualmente:
   la abrirá el runner con su owner tras la aprobación.
7. Avisar «ya podés aprobar», con hora local exacta de cierre. El usuario pulsa
   una vez Approve and deploy. El preflight del workflow comienza inmediatamente;
   aprobar cuando el gateway sigue completamente cerrado lo haría fallar con 503.
8. Confirmar por API la aprobación de `possee41` y el avance del mismo job.
   Si no aparece, revisar el error de esa misma pantalla, sin otro dispatch/rerun
   ni clics repetidos. Cerrar si vence el plazo o el usuario solicita detenerse.
9. Tras finalizar, cerrar gateway y controles, comprobar cero leases y estado
   de la misma ejecución, preservando secretos y sin activar schedule.

La mejora propuesta es de coordinación y verificación visual. No se propone
quitar reviewers, permitir bypass, cambiar el SHA o ampliar los límites.
