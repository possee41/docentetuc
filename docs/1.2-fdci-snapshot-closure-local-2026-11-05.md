## Diagnóstico y corrección del snapshot

La cuarta solicitud del último ensayo fue `POST /api/internal/fdci-automation/delta`, operación `snapshot`, versión `065d8517-3edd-48f5-94db-c7d1c6655e7f`, Ray `a55bbc6a18e5287d`: HTTP 200, outcome ok, CPU individual **8 ms**, wall time **711 ms**. No alcanzó staging ni publicación. Fuente: informe y evidencia del ensayo anterior; no se repitió remotamente.

El camino completo realiza tres controles SQL (suspensión, identidad y concesión) y tres lecturas del snapshot (estado, cola y confirmados). No normaliza publicaciones ni calcula sus hashes: devuelve hashes existentes y estado, sin payloads de candidatos. La hipótesis respaldada es el costo de los cruces D1 y de sus conversiones/serialización; no hay un perfil remoto que permita atribuir exactamente los 8 ms. El tiempo de espera de D1 no es CPU.

Se agruparon estado y cola en un único `DB.batch` de lectura, conservando el orden estado→cola. La consulta de confirmados sigue dependiendo del espacio restante: no se duplican lecturas para calcularlo ni se amplía la respuesta. Se mantienen el techo combinado de 200 hashes, el lookahead, paginación, revisión/CAS y todos los controles previos. Cuando `queuedAfter=null`, no se agrega ninguna consulta de cola. No se modifican auditoría, candidatos, cursor ni reglas de escritura.

## Causa del 403 y cierre corregido

El recibo anterior registra a las 12:07:33.532Z HTTP 403, código 9109, `Invalid access token`, durante la identificación administrativa de cuenta, antes de ejecutar el cierre. No fue un rechazo de la credencial de importación FDCI. La recuperación independiente se produjo después de consultar `wrangler whoami` en un proceso nuevo.

Defecto demostrado del ejecutor privado `.wrangler/fdci-pending-admin.mjs`: retenía el OAuth en memoria y lo inyectaba como `CLOUDFLARE_API_TOKEN` en **todos** los hijos Wrangler, incluido `auth token`. La implementación instalada de Wrangler (`auth token` en `node_modules/wrangler/wrangler-dist/cli.js`) prioriza `getAuthFromEnv()` frente al OAuth local; por ello podía devolver el mismo token inválido y bloquear su renovación normal. No se puede establecer si Cloudflare lo invalidó por expiración, revocación u otra causa.

Corrección versionada en `scripts/fdci-canary-closure.mjs`, integrada localmente en ese adaptador privado, que permanece fuera de Git:

- Los hijos Wrangler reciben un entorno sin tokens/API keys Cloudflare heredados. Nunca se reinserta el OAuth cacheado como API token.
- `freshOAuth(run)` ejecuta `whoami --json`, permitiendo a Wrangler renovar su sesión OAuth existente, y luego obtiene `auth token --json`. Captura ambas salidas, acepta exclusivamente OAuth y devuelve errores sin imprimir valores sensibles. No inicia login ni amplía permisos.
- Antes de cada barrera, el adaptador renueva autenticación y verifica cuenta/D1 exactas. `closePendingCanary` además fija nombre, UUID, binding, cuenta y configuración cerrada del canary exclusivo.
- El marcador local de detención se escribe primero. Se intentan por separado: retirar exposición, HALTED/expirar concesión, configuración cerrada, retirar secreto y verificar el cierre. Un fallo no omite las otras barreras. No hay reintentos automáticos de mutaciones ambiguas.
- El secreto se elimina solo si existe. El estado final se comprueba por metadatos y SQL acotado: exposición y previews deshabilitados, cero rutas/dominos/Cron, flags cerrados, sin secretos, HALTED y cero concesiones vigentes. También se conservan los controles existentes de candidatos/cursor y otros Workers. Los errores intermedios siguen registrados aunque la verificación final confirme el cierre.

Integración mínima reproducible del adaptador: `run` usa `oauthEnvironment(env)`; `auth` borra el token anterior y obtiene `freshOAuth(run)` antes de comprobar identidad; la rama de cierre llama `closePendingCanary({auth, api, sql, run, metadata, verifyClosed}, config)`, conservando su verificación final existente. No debe existir un `await auth()` global antes de esa rama: impediría intentar las barreras independientes. El módulo no ejecuta operaciones al importarse ni posee credenciales.

**Límite real:** si la sesión ha sido revocada o Cloudflare no está disponible, ningún cliente puede garantizar el cierre administrativo. En ese caso se registra cierre NO CONFIRMADO y se detiene todo; no se inicia otra corrida. Los TTL, ventana finita, suspensión persistente y umbral de 7 ms permanecen intactos. No se promete resolver una revocación de sesión sin intervención humana.
